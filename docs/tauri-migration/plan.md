# 分阶段开发计划

工作量不使用未经验证的工期承诺。以下阶段门槛优先于进度百分比；实际状态见 [tracker.md](tracker.md)。所有阶段遵循 [architecture.md](architecture.md) 的前端可优化边界。

## P0 — 基线、依赖和关键技术验证

任务：MIG-001–004。输入为当前 Wails 源码和可复现的基线构建。

- 记录 Go/Node/Wails/Rust/MSVC/WebView2 环境与可用目标架构；保留基线提交和产物摘要，不执行无必要的依赖升级。
- 盘点全部 Backend/runtime 调用、事件、默认值、数据布局、托盘及启动行为；采集脱敏数据 fixtures 和视觉基线。
- 检查官方插件/候选 crates 的准确版本、维护状态、许可证、支持平台；锁定最少依赖组合。
- 做边界原型：管理员 Tauri WebView、单实例、隐藏启动、最高权限延迟自启、动态内核路径、优雅退出/崩溃恢复、便携更新、旧客户端过渡。原型验证后删除无用脚手架。
- 明确 Windows 最低支持版本、x64/ARM64 验证安排、便携/安装模式、数据路径与回退策略。

退出条件：关键能力有证据或明确阻断；便携更新/权限/数据方案已记录，不能以“之后研究”进入依赖这些决策的实现。常规选型自行决定；改变批准范围才提交用户确认。

## P1 — Tauri 外壳与前端接入

任务：MIG-005–006；依赖 P0。

- 建立 Tauri 2 工程，复用现有 Vite/Vue 与资产，不重建 UI。
- 完成窗口、Mica/主题、托盘、单实例、隐藏启动、关闭行为及清理入口骨架。
- 建立薄 API 层、类型化 DTO 与统一错误；直接更新 imports、composables 和事件管理。临时兼容桥必须有移除条件。
- 去除版本信息对 `wails.json` 的长期依赖，适配拖动区域，配置最小 Tauri permissions/CSP。
- 对尚未迁移的功能明确开发状态，不将 mock 结果当功能验收；发行产物不允许依赖假后端。

退出条件：现有界面可在 Tauri 运行，桌面行为与视觉通过；通信类型和订阅生命周期通过检查，未迁移功能清单明确。

## P2 — 存储、配置与订阅

任务：MIG-007–008；依赖 P1 和数据路径决策。

- 实现路径、旧数据加载/导入、持久化、恢复、设置和订阅管理。
- 迁移覆盖配置、IPv6/日志配置处理、内核配置校验及版本读取。
- 使用现有文件布局，避免无必要 schema 重写；保留可恢复备份。
- 完成应用日志与内核日志接口，保持内容与交互，删除重复前端请求/状态。

退出条件：正常、缺字段、损坏、中断、中文/空格路径等 fixtures 通过；写入失败不伪报成功；旧数据不丢失；配置语义与无关字段保留有检查。

## P3 — Windows 核心能力

任务：MIG-009–011；依赖 P2。

- 完成内核协调、模式切换、重启、进程退出、日志与流量、智能连接。
- 实现系统代理状态归属和恢复、权限失败处理、自启任务迁移、UWP。
- 所有入口共用状态来源；取消和退出收尾有边界；快速点击/托盘并发不得产生多内核或卡死状态。

退出条件：Windows 三种模式、网络故障、启动失败、内核崩溃、应用重启、自启与 UWP 实机验收通过。清理不会影响其他软件进程或代理。

## P4 — 更新、构建与发行演练

任务：MIG-012–014；依赖 P3 和 P0 的更新方案。

- 分别完成内核事务式更新和应用签名更新，保持镜像、预发布及进度交互。
- 落实旧 Wails 客户端→首个 Tauri 版本→后续 Tauri 版本的过渡，不给旧客户端投喂不兼容资产。
- CI 使用 Tauri 官方 action/工具链，锁版本、构建 x64/ARM64，并分别收集运行证据。
- 版本只有一个权威源；发布元数据和签名产物对应同一版本。密钥经 CI secrets 注入，更新签名与 Windows Authenticode 分开记录。
- PR 只验证构建，签名/发布使用适当受控流程；不沿用任何不合适的推送即发布行为。

退出条件：在测试发布源完成升级、拒绝错误签名、错误架构、下载中断、替换失败、恢复演练；无密钥时相关任务标 blocked，不能假装完成。实作演练不等于获得正式发布授权。

## P5 — 全量验收与移除旧栈

任务：MIG-015–017；依赖 P4。

- 执行完整 validation 矩阵；同环境比较启动、空闲 CPU/内存、托盘后台负载、日志压力和退出清理，记录基线与候选数据。P0 确定可复现测量方法，不凭感觉声称更快。
- 同场景比较主题、缩放、Mica、布局和动画，以及全部操作路径。前端简化必须保持效果。
- 移除 Go/Wails、临时桥、旧配置及构建依赖；扫描源码、文档、忽略规则、CI，保留历史资料中必要的迁移说明。
- 更新项目 README、开发/发行/恢复说明；确保新环境按文档可构建；关闭阻断项并完成交接。

退出条件：总体验收通过，无孤立旧调用和双版本源；Linux 能力未被误报；任务与证据齐全。删除旧栈在功能验证后执行，不能先删再寻找行为依据。

## 分阶段回退

- 开发回退：保持小而可审查的提交，每个阶段可独立回退；不以破坏用户未提交修改的 reset/clean 作为常规手段。
- 数据回退：使用迁移前备份与隔离测试目录；明确新版本写入后旧版是否可读，不能承诺无条件降级。
- 内核回退：保留旧二进制与有效配置，恢复后重新验证运行；系统代理也恢复到一致状态。
- 应用回退：先停止应用与内核，使用已验证的旧产物和对应数据备份。具体安装版/便携版步骤由 MIG-013 固化，签名策略不为回退关闭。
- 删除旧构建链前保留基线 tag/提交和构建说明；不强制在本次文档任务创建 tag 或发布。
